# T068 Webhook 签名离线核验

## 1. 功能内容

本地HMAC-SHA256 / SHA384 / SHA512完整签名核验。输入原始请求字节、明确算法/签名格式及本地密钥，输出匹配布尔值、消息字节数/SHA256和解释。可额外选择一份参考请求，比较全部字节差异总数和前100个0起偏移；不输出字节值。支持完整JSON/Markdown新副本，不发送请求。

## 2. 为什么需要

Webhook核验失败可能来自原始字节被JSON重序列化、换行变化或密钥/算法/供应商拼接规则不同。这个工具对明确原始字节离线核验，不自动格式化JSON，也不把不匹配直接归咎于密钥。提供可重现的RFC固定向量和参考字节对照，帮助排查接收端输入处理。

## 3. 实现方式

使用浏览器WebCrypto `importKey(raw,{name:'HMAC',hash},extractable:false,['verify'])` 和 `subtle.verify`，不自行用普通字符串比较签名，也不导出密钥。SHA256另作消息摘要，不作密钥指纹。支持直接签完整body的通用HMAC，hex/标准带padding Base64完整签名，以及GitHub `sha256=`完整头值（只能SHA256）。拒绝算法不在白名单、截断签名、错误长度、非规范padding、空格/0x前缀、URL Base64及孤立Unicode代理项，不trim密钥或签名。

参考 [RFC4231 HMAC测试向量](https://www.rfc-editor.org/rfc/rfc4231)、[WebCrypto verify](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/verify)、[GitHub webhook核验规则](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)。GitHub模式只处理这里的body和sha256头，不读取真实网络header；Stripe/Slack等带时间戳前缀方案、RSA/Ed25519、SHA1、签名多版本列表、重放/时钟窗口不在本模式范围。匹配只证明本次密钥、算法、签名字节与消息一致，不验证发送者身份、新鲜度、事件权限或业务内容。

消息最多2MiB，密钥1–4096字节，参考消息最多2MiB。文本入口按UTF-8编码、不作Unicode规范化，但textarea按浏览器规则把换行转LF；核对原请求应选择文件或hex。文件使用File.slice/arrayBuffer分块读取，长度核对，保留BOM、CRLF、NUL、无效UTF-8和全部二进制字节，不解码/解压。核验作业捕获独立输入与AbortController，模型复制字节快照，避免取消后编辑或调用者修改混入旧作业。

比较参考时逐0起偏移统计全部差异，包括长度多出的尾部；插入或删除后后续错位可能产生多项差异，不是最小编辑距离。偏移示例最多100，显式 `offsetExamplesAreComplete:false`，differenceCount仍覆盖整个输入，不把100项示例当完整差异清单。报告不含原始消息、密钥、原签名、参考字节值或文件名；长度/SHA仍可能透露文件关联，分享前核对。

没有配置/localStorage/sessionStorage、网络、后台监听或自动历史。清空、隐藏、切走、销毁清空当前控件和File引用、废弃结果/预览并取消票据；晚结果不能重现。已复制密钥字节、签名字节和作业字节在结束/失败后fill(0)，CryptoKey不可提取并释放引用。JavaScript字符串、浏览器undo/内部Crypto执行、进程/操作系统内存不保证安全擦除；不把这些措施宣称密钥保险箱。WebCrypto没有取消底层运算，取消只是停止等待/展示，原生保存已经写出的文件不会撤回。

## 4. 如何使用

1. 工具工作台打开 T068，选消息来源：UTF-8文本、完整hex、或原始字节文件。文件模式再选择原请求文件。
2. 明确密钥编码（UTF-8/hex/标准Base64），输入本地密钥。空格参与计算，勿默认删除。
3. 明确HMAC算法及完整签名格式；GitHub填 `sha256=...` 头值，不填header名称。
4. 可选参考文件，点击“离线核验完整原始字节”。匹配或不匹配都查看口径和消息摘要；参考差异不自动解释失败原因。
5. 预览完整JSON或Markdown，再保存报告新副本。必须有公共 `saveTextSupportsCopyOnly===true`，传copyOnly:true，只有ok===true才成功；已有目标拒绝、取消/失败不丢预览，partialPath供人工核对。清空或离开后需重新输入密钥，不自动恢复。

## 5. 产出与具体例子

产出 `webhook-hmac-report-copy.json/.md`，完整包含feature/version、algorithm、signatureFormat、match、bodyBytes、bodySha256、providedSignatureBytes、三项省略声明、可选byteDifference及适用边界。Markdown完整JSON不是当前页摘要；不包含原始密钥、消息或签名。

“载入 RFC4231 固定示例”使用公开练习密钥hex `0b`重复20次，body UTF-8为 `Hi There`（8字节），HMAC-SHA256完整hex为：

```text
b0344c61d8db38535ca8afceaf0bf12b881dc200c9833da726e9376c2e32cff7
```

运行应match=true；把body改为 `hi There`，保留密钥与签名再核验，match=false。选择原 `Hi There` 字节文件作参考，修改后的第0字节不同，differenceCount=1、firstDifferenceOffset=0。把签名缩成 `00` 应报格式/长度错误，没有匹配报告；不是简单match=false。

实际原始文件含UTF-8 BOM、0xff、NUL及CRLF时，文件模式保留它们；用文本粘贴重建会改变这些字节，因此不互相冒充原始输入。GitHub模式可把正确SHA256前加sha256=；切换SHA512则该格式被拒绝，需完整64字节hex/Base64模式。
