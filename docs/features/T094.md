# T094 联系人迁移与冲突核对

## 1. 功能内容

从用户提供的本地联系人 CSV 或 vCard 3.0 文本建立统一联系人，保留来源编号、原始记录序号、物理起止行、原字段/属性和未映射审计。姓名、邮箱、电话、地址、备注作为基础字段；CSV 映射由用户明确确认。只比较本次加入的来源，不访问云通讯录，不请求账号、网络、AI、摄像头或麦克风。

同邮箱、同电话或同名产生人工候选，默认全部保留；姓名不同也不会被自动覆盖。用户可逐对选择保留两条，或先指定五种字段的优先来源、预览拟合并联系人、再确认合并。合并前两条完整记录保留在元数据，避免姓名优先级和精确去重并集造成原信息消失。JSON、CSV、vCard 及冲突/未映射报告都经完整文本预览后创建新副本。

## 2. 为什么需要

不同设备的联系人导出表头和字段范围可能不同，直接按同名或同邮箱合并容易把另一人的姓名、号码或备注吞掉。明确映射解决字段对齐问题；候选保留、人工优先级和来源物理行解决是否同一人的判断问题；原记录和未映射信息解决迁移审计与可追溯性。

例如“林晓”和“林小晓”拥有同邮箱，手机号分别使用本地和带国家码的写法。本功能把邮箱匹配作为核对线索，不声称号码相同、不推断身份；用户确认后保留两个原号码、两条原记录和未映射标签。保留两条是一个完整可导出的结果，无需为了结束流程强行合并。

## 3. 实现方式

- `meta.json` 注册“工具 / 隐私与数据迁移”；`index.js` 使用公共 `h()`，同步 `create(root)` 返回生命周期。纯模型 `model.mjs` 自包含 CSV 与受限 vCard 解析器，未运行时引用其他功能或待选第三方解析库，未修改 main/preload/registry。
- CSV 接受逗号分隔、LF/CRLF、双引号转义、引号中换行和空字符串。非空唯一表头使用 NFKC 检查重复，无首尾空白或控制字符；每条记录列数必须完全一致。不静默跳过空记录或补列。记录的物理起止行包含引号内换行，来源编号与记录编号始终可对照。姓名最多映射一列；邮箱和电话的每个映射单元格作为一个值，不自动拆分分号列表。未映射列和无法按比较规则识别的邮箱进入审计，原值仍完整保留。
- vCard 只接受独立 `BEGIN:VCARD`/`END:VCARD` 卡片与唯一 `VERSION:3.0`。支持 FN、五部分 N、EMAIL、TEL、七部分 ADR、NOTE、空白/制表符折叠行及 `\\`、`\;`、`\,`、`\n` 文本转义。折叠后保留物理属性起止行。N 可生成展示姓名，FN 优先。不同版本、任何 ENCODING 参数、非 UTF-8 CHARSET、非法转义或不完整卡片阻止整个来源导入，不保留该来源的部分结果。
- 未支持的属性、参数/分组信息、重复姓名、错误结构以及 N/ADR 内未转义逗号表示的复合值不被默默抹除；完整展开属性行保存在未映射审计和原属性中。基础字段并不承诺保存 TYPE 等标签到目标通讯录的标准字段；原信息保存在扩展元数据，提示使用者检查目标软件。vCard 输出缺少非空姓名 FN 时明确拒绝该格式，JSON/CSV 仍可保存，不编造身份。
- vCard 3.0 基础语法和字段范围参考 [RFC 2426](https://www.rfc-editor.org/rfc/rfc2426)；内容行展开参考 [RFC 2425](https://www.rfc-editor.org/rfc/rfc2425)。导出行按 UTF-8 最多 75 字节折叠，换行和标点转义后再输出。这里只实现上述范围，不宣称完整 vCard 标准兼容。
- 邮箱比较仅修剪首尾空白、将域名转小写；local-part 大小写保留，不移除 `+tag`、不去点、不做 IDNA 或供应商别名猜测。原值输出不变。电话只有简单数字格式参与候选，比较修剪首尾空白后的原字符串，国家码、`+`、连字符、括号及内部空格均不归一化。同名比较修剪首尾空白后精确匹配，仅提供候选。
- 手工合并只接受当前候选中的两个原始 ID。五个字段优先来源各从这两个 ID 选择；姓名取优先来源第一个非空姓名，其他字段精确去重并集、优先来源值在前。两个原始对象、原字段、原属性、未映射值和出处完整保留。一个 ID 最多参与一个合并，重叠合并会明确拒绝；不自动传递合并三人。撤销原合并后才能重新选择。与已确认合并共享 ID 的候选明确标记，不再继续吞并。
- 合计限制 1 MiB UTF-8、10 个来源、1000 联系人；CSV 100 列、单元格/展开属性 65536 字符；每张 vCard 100 属性、单来源 20000 物理行；最多 5000 对候选；每种导出格式 8 MiB。超过限额明确拒绝，无静默截断；可减少来源或分批处理。签名、邮箱验证服务和外部通讯录解析均不在流程中。
- 异步核对每 50 联系人或 200 次高密度候选比较让出事件循环。取消、隐藏、暂停、输入编辑、来源移除或替换使旧任务失效；当前任务返回前不启动第二个。新对照输入或 CSV 映射会废弃所有旧人工判定、拟合并预览和导出预览；迟到读取/进度/保存回调不能恢复旧状态。销毁清空来源文本和状态、移除监听，不写全局配置。
- 导出只调用支持副本保护的 `saveText({ content, extension, defaultName, copyOnly: true })`，先检查 `saveTextSupportsCopyOnly`。实际目标路径在原生保存对话框选择，已有文件不能被覆盖。只有 `ok === true` 显示成功；取消、返回 false/undefined 和异常保留当前预览与判定。宿主错误可能含路径，因此界面不直接暴露错误原文。显示内容均为文本节点，不把姓名/备注作为 HTML 运行。

## 4. 如何使用

1. 输入来源名称，选择 CSV 或 vCard 3.0，粘贴文本或读取一个严格 UTF-8 文件。文件扩展名只帮助选择格式，不代替语法校验；读取不保存原路径。
2. 点击“解析当前来源”。CSV 的建议映射可逐列更改，至少映射一个基础字段；不需要映射的列选择“未映射（保留审计）”。vCard 展示基础联系人数量和未映射/参数信息数量。
3. 点击“确认映射并加入来源”，再输入下一来源。加入完成后草稿清空，已加入来源文本仍在本面板内存。可“编辑 Sxxx”：该旧来源立即移除，修改后重新解析加入会得到新 ID；也可直接移除来源。两种操作都会清除旧判定。
4. 点击“重新核对全部来源”，查看统一联系人（每页 20 条）、候选（每页 10 对）及来源/行号。未确认前输出数量等于原始数量。“保留两条”表示本对不合并，可以直接导出。
5. 拟合并时逐字段选优先来源，点击“预览合并 <ID 对>”，查看拟合并对象和原记录；点击“确认此合并”才影响输出。取消预览不应用；“撤销判定”重新按其余当前判定生成输出。共享已合并 ID 的候选不可继续合并。
6. 选择 JSON、CSV、vCard 或冲突与未映射报告的完整预览，再保存当前预览新副本。在原生保存对话框确认路径。报告及扩展元数据含原联系人与未映射原值，请确认分享范围。
7. “清空当前草稿”保留已加入来源，但废弃核对与判定；“清空所有来源与结果”删除面板内存中的源文本、来源、判定和预览。切换具体功能会销毁未保存状态；整个工作台暂停会取消在途任务，已经完成的结果可以在同一面板恢复。取消无法中断已发出的 File 读取，但返回内容会被丢弃。已弹出的原生保存对话框仍由用户取消或完成。

## 5. 使用后产出

- JSON：`{ feature: "T094", version: 1, contacts, report }`，联系人带 canonical 基础字段、来源/物理行、未映射值、原 CSV 字段/vCard 属性；合并对象另带 `mergedFrom` 和两条完整 `originals`。
- CSV：`id,name,emails_json,phones_json,addresses_json,notes_json,metadata_json`。列表列以 JSON 字符串保留多值和结构，元数据包含来源、原字段/属性及合并前对象；CSV 正确转义逗号、引号和多行内容。这是可审计的统一 CSV，目标通讯录导入时须按其要求映射/转换列表列，不宣称所有通讯录可直接无损导入。
- vCard：基础 FN/N/EMAIL/TEL/ADR/NOTE 加 `X-T094-METADATA` 文本扩展保存完整元数据。标准基础字段可交换，未支持属性及标签不假称已写入目标软件的原字段。目标应用可能忽略扩展，因此同时保存 JSON 或审计报告更便于核对；当前工具重新读入此 vCard 时扩展信息作为完整未映射属性保留，不能假称恢复为内部 merge 状态。
- JSON 审计报告：来源、输入/输出数量、候选原因和状态、已选字段优先级、未确认数量、未映射原值和物理行，以及明确的比较/合并规则。未确认候选输出两条；同邮箱不同姓名不会在导入时被删除或改名。

所有副本写入新文件，不修改源文件；保存成功、取消及失败均有准确状态。未映射审计不是匿名报告，带原值是为了核对迁移是否丢信息。

## 6. 具体例子、验证与限制

点击“填入来源 A 演示”后“确认映射并加入来源”，然后点击来源 B 演示并加入，再核对：

```csv
name,email,phone,tag
林晓,lin@example.test,13800138000,旧设备标签
```

```csv
name,email,phone,tag
林小晓,lin@EXAMPLE.TEST,+8613800138000,新设备标签
```

应显示原始 2 条、输出 2 条、未确认 1 对、未映射 2 项。候选 ID 为 `S001-C0001|S002-C0001`，原因只有邮箱匹配；电话不同写法不被归一化。直接预览 JSON 仍有两个人。选择五个字段都优先 `S002-C0001`、预览合并，输出仍为两条；点击确认后变为一条，“林小晓”、优先来源邮箱/电话排在前，仍保存两邮箱、两电话号码、两个设备标签及 `originals` 中两条原联系人。撤销判定恢复输出两条，旧导出预览必须重建。

vCard 例子：

```text
BEGIN:VCARD
VERSION:3.0
FN:林晓
N:林;晓;;;
EMAIL;TYPE=INTERNET:lin@example.test
TEL:13800138000
ADR:;;街道\;一号;城市;地区;100000;中国
NOTE:第一行\n第二
 行
X-TEAM:研发组
END:VCARD
```

NOTE 的空格折叠行展开为“第一行\n第二行”，转义换行为真实换行；ADR 的街道包含字面分号。`X-TEAM` 和 EMAIL 参数的原属性进入审计，属性物理行可追溯。把 VERSION 改为 4.0 或加入 `ENCODING=b` 时整来源拒绝，无法加入或改写；其他已加入来源保留。
