# T081 · 跨时区会议窗口

所属分组：工具 / 个人效率与生活计算。规格对应 `docs/feature-planning/tools.json` 的 T081。

## 功能与必要性

跨时区协作不仅要换算小时差，还要判断日期、夏令时和各方可用区间。伦敦与香港夏季相差7小时，冬季相差8小时，固定减小时数会产生错误。当地时钟在某些日期还会跳过或重复一段时间。本功能在本机核对输入、求公共可用窗口，并生成含UTC及每位参与者完整当地日期的邀请文本。

支持每人多个明确可用区间、重叠区间合并、会议时长和候选间隔。它与专注计时和任务清单的目的不同；结果是可核对的时间方案与文本，不发送邀请或创建日历事件。

## 实现方式与官方依据

- `meta.json` 提供工作台发现所需 ID、分类、分组、标题及说明。
- `index.js` 使用现有 `h` 创建日期、时间、IANA时区、偏移模式和区间控件。同步 `create` 返回生命周期；切走取消计算，销毁清空内存状态。界面显示输入区间解释、公共窗口、候选时段和邀请预览。
- `model.mjs` 独立执行日期验证、当地时间反向核验、UTC区间交集、候选生成和邀请文字生成，无新增依赖。
- 所有计算都显式指定时区，使用 `Intl.DateTimeFormat` 的公历、拉丁数字与 `h23` 小时周期，并用 `formatToParts` 获取字段。不会将无偏移字符串传给 `Date.parse` 让电脑的当地时区隐式决定结果。

实现前已核对 [TC39 ECMA-402 IANA 时区要求](https://tc39.es/ecma402/#sec-use-of-the-iana-time-zone-database)、[DateTimeFormat 的创建过程](https://tc39.es/ecma402/#sec-createdatetimeformat)、[formatToParts](https://tc39.es/ecma402/#sec-intl.datetimeformat.prototype.formattoparts) 和 [ToLocalTime](https://tc39.es/ecma402/#sec-tolocaltime)。规范提供按时区从时刻得到当地字段的机制；当地日期和时刻的反向消歧由本功能显式完成。

当地模式按分钟精度枚举完整±24小时偏移范围，并将候选UTC时刻重新格式化到IANA时区，只有年月日时分完全一致才是有效候选。零候选报不存在；多候选报重复并列出UTC候选和偏移，不自动选择。每512个候选让出事件循环并检查取消；一个计算内缓存重复起止边界。若运行时返回非整分钟偏移或不支持所需格式，明确报不支持。

公共窗口在UTC时刻上合并和求交，按实际经过分钟计算长度。候选从每个公共窗口的起点开始、按设置间隔递增，只保留能够完整容纳会议的起点。所有输出通过当前运行环境的IANA规则转回当地日期和偏移。

## 使用方式

1. 填写会议标题、时长（分钟）、候选起点间隔（分钟）。初始界面是2026年7月伦敦与香港示例，也可使用“跨日示例”。
2. 为每位参与者填写名称/城市标签和IANA时区。下拉建议提供运行环境支持的名称，也可直接输入，例如 `Asia/Hong_Kong`、`Europe/London`、`America/New_York`、`UTC`。城市标签不参与时区推断。
3. 添加可用区间，每段明确填写开始日期/时刻和结束日期/时刻。可以给同一人添加上午、下午两段，最多4段。跨日直接填写次日结束日期。
4. 点击“计算公共窗口”。先检查输入区间的UTC及当地实际解释，再核对公共窗口是否足够容纳会议。
5. 选择候选时段，检查每位参与者完整日期、时刻、UTC偏移和时区。邀请文本可复制或另存；公共窗口和原始输入可保存为JSON报告。
6. 保存对话框显示最终路径，副本保护拒绝已有文件。修改区间、时区、时长或间隔后原计划失效，必须重新计算。

## 输入规则与具体例子

### 当地时间与明确偏移是两种独立语义

- **当地时间模式**：日期和 `HH:mm` 是所选IANA时区的墙上时间。夏令时不存在或重复的端点报错。
- **明确UTC偏移模式**：日期和 `HH:mm` 按用户填写的 `Z` 或 `±HH:mm` 解释。所选IANA时区只用于核对和邀请展示，并不覆盖这个偏移。开始与结束可填不同偏移，适用于夏令时回拨。界面始终显示解析后的实际当地时间，便于发现输入与所选时区不一致。
- 时间精度为分钟，不支持秒或 `24:00`。日期为2000至2100年的真实公历日期；24:00请填写次日00:00。偏移范围为 -14:00 至 +14:00，分钟须00至59，14小时偏移只允许00分钟。
- 不接受 `PST`、`BJT` 等可能有歧义的简称，不将“London”等城市名静默转换为时区；IANA别名如运行环境支持可正常使用。
- 结束必须晚于开始，实际跨度最多7天。重叠或相接的同人区间合并；不同参与者窗口仅在一个端点相接时，不能容纳正时长会议。

### 规格验收：伦敦与香港

参与者1：`Europe/London`，2026-07-01 09:00至12:00；参与者2：`Asia/Hong_Kong`，2026-07-01 16:00至18:00。会议30分钟、间隔15分钟。

公共窗口为 `2026-07-01T08:00:00Z` 至 `2026-07-01T10:00:00Z`，可用120分钟，共7个候选起点。第一候选：

```text
UTC：2026-07-01T08:00:00Z → 2026-07-01T08:30:00Z
伦敦：2026-07-01 09:00 UTC+01:00 → 2026-07-01 09:30 UTC+01:00
香港：2026-07-01 16:00 UTC+08:00 → 2026-07-01 16:30 UTC+08:00
```

冬季2026-01-01的伦敦09:00对应香港17:00；不能沿用夏季差值。

### 跨日及UTC日期

洛杉矶 `America/Los_Angeles`：2026-07-01 16:00至18:00；香港：2026-07-02 07:00至09:00。120分钟会议公共窗口为 `2026-07-01T23:00:00Z` 至 `2026-07-02T01:00:00Z`。

输出同时保留洛杉矶7月1日、香港7月2日，以及UTC开始/结束的两个不同日期。午夜使用00:00，不显示成同日24:00。候选间隔以窗口开始为基准，例如09:07开始、间隔15分钟时，起点为09:07、09:22，而不静默向09:15取整。

### 夏令时不存在、重复与实际时长

- 纽约2026-03-08 02:30不存在，当地模式报错；不会顺延到03:30。
- 纽约2026-11-01 01:30重复，当地模式要求消歧，并展示 `2026-11-01T05:30:00Z` / UTC-04:00 和 `2026-11-01T06:30:00Z` / UTC-05:00。切换明确偏移后可选择所需时刻。
- 明确偏移输入“2026-03-08 02:30 -05:00”是一个有效时刻，按所选纽约IANA规则显示为03:30 UTC-04:00。这是明确偏移输入的语义，不是当地模式偷偷顺延。
- 回拨区间开始2026-11-01 01:45 -04:00、结束01:15 -05:00，实际时长30分钟，尽管墙上时刻看似倒退。
- 春季区间01:30至03:30实际只有60分钟，不是120分钟。测试也覆盖 `Australia/Lord_Howe` 的半小时回拨、`Pacific/Apia` 的整日跳过及 `Asia/Kathmandu` 的15分钟倍数偏移。

## 产出与限制

- 界面：逐人已解释区间、公共窗口、实际可用分钟、最多200个候选和每人当地会议起止。
- TXT邀请：标题、会议实际分钟数、UTC完整起止、每人完整日期/时刻/偏移/时区。复制只写本机剪贴板。
- JSON报告：功能ID、输入、所选候选、计算方案和邀请文本。可追溯明确偏移与当地模式的不同解释。
- 保存调用 `files.saveText({ content, extension, defaultName, copyOnly: true })`，要求 `files.saveTextSupportsCopyOnly === true`；基础层以 `wx` 拒绝已有目标。旧基础层允许计算及复制，导出禁用并说明原因。
- 最多8位参与者、每人4段、每段实际7天；会议时长1至1440分钟、间隔1至120分钟。超过200个候选仍报告总数和完整公共窗口，界面只展示前200个，可增大间隔或缩小区间重新计算。
- 输入为明确日期区间，不自动扩展每日工作时段、节假日或循环会议。数据仅存本次界面内存，不上传、不读取外部日历、不更改系统时区。
- 时区规则使用当前Electron/Node的ICU/IANA数据库。未来政府规定变化或旧运行时数据库可能影响结果；更新运行环境并在会议前复核。分钟精度及限定日期范围内验证，历史秒级偏移明确不支持。
